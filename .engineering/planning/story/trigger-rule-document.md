## Outcome

`canon-trigger/1` exists: one rule per document with `id`, `version`, `owner`, `subject.kind`,
`subject.state`, `where`, `start.protocol`, `start.input`, `mode`, `access`, `refire` and `cap`
(design § 3), and `canon trigger validate <file>` accepts a valid document and refuses an invalid
one naming the field.

## Why

Request acceptance 1. Every later story reads this document.

## Scope

- **In:** the Rust model and parser of `canon-trigger/1` (unknown fields refused); the row fields
  the rule declares under `subject.fields` (type `string`, `integer`, `decimal` or `bool`, optional
  or not), `$row` being a closed record of them; `subject.state.field` a declared required `string`
  field; `where` compiled with `canon-expr/1` against a catalog the kernel builds per rule from
  `Pure` builtins only (`contains`, and a presence test per optional field type), with no change to
  `canon-expr/1`; `start.input` values `{field}` naming a declared field or `{const}`; the rule key
  `<id>@<version>`; `canon trigger validate --path <file>`; the reference page generated by
  `canon-docs`.
- **Out:** checks across documents or against protocols (story:trigger-rule-publication);
  evaluation, including `undetermined` for a missing or wrongly typed field
  (story:trigger-evaluate).
- **Decided during the story (coordinator):** row fields are declared, because `canon-expr/1`
  types field access only on a closed record; the alternative, a `row` type inferred by the
  checker, would change the language.
- **Open for later stories:** a `protocol/1` case input takes values from a closed list, so a
  `{field}` mapping of a row value such as an id cannot fill one today; story:trigger-evaluate or
  story:trigger-rule-publication settles what a row value maps to.
- **Surfaces:** a new module `crates/canon/src/trigger/`, `crates/canon-cli/src/lib.rs`,
  `ess/domains/trigger.yaml`, `ess/domains/cli.yaml`, `conformance/`, `website/docs/reference/`.

## Acceptance

A document with every field validates. Missing `owner`, `subject`, `start.protocol` or `mode`
fails naming that field; `mode: sometimes` or `access: admin` fails naming the field; a `where`
that calls a function outside the catalog fails naming `where`; an input mapping with an
expression fails naming `start.input.<name>`. Each case is a conformance scenario.

## ESS first

First commit: `ess/domains/trigger.yaml` declares `canon-trigger/1`, `cli.yaml` declares
`trigger-validate`, and the conformance scenarios above; `ess_model_matches` and
`ess_commands_match` fail on it (red recorded).
